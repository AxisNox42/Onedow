# 실행 가능한 점검표 — 구조·결함·동작 변경 분리

2026-10-12 보강. **이 문서의 수정·테스트 항목은 계획이며 아직 구현하거나 실행하지 않았다.** CI 실패 로그만 실제 원격 기록을 읽어 확인했다. D01~D40은 구조 리팩터링, FIX는 결함 수정, BEH는 확정 동작 변경, API는 입력 계약 조사다. 서로 다른 변경은 별도 diff/커밋과 검증 결과로 추적한다. GitHub 이슈 생성이나 담당자 배정은 하지 않았다.

결정 역할: **구현**=작업 수행 개발자, **검토**=코드 리뷰 담당, **규칙**=사용자(게임 규칙 담당). 실명 배정은 아직 없다. 일상적인 기술 정리는 구현·검토 담당이 판단하고, 미정 게임 규칙만 사용자 결정이 필요하다. 완료는 아래 증거가 있을 때만 표시한다.

순서: 결함 복구(FIX) → BEH별 실패 테스트/작은 수정/통과 확인 → 수정된 동작의 기준 확정 → D 항목 구조 이관 → 같은 기준 회귀 검증. BEH를 처리하기 위해 작은 helper가 꼭 필요하면 해당 diff에 명시하고, 광범위한 보상 통합은 D01에 남긴다. 구조 변경과 함께 숫자나 보상 규칙을 바꾸지 않는다.

미결 결정은 관련 항목의 이관만 막는다. DEC-01: 대혼란의 전쟁군주 스택. DEC-02: Creative/DYING 회복·집계. DEC-03은 2026-10-13 확정: 시련 HP 감산 후 HP 증강 적용, `baseFireInterval`은 무기 적용 후·증강 전 값. DEC-04는 확정: 투척 스웜을 무한 세례 처치 누적에서 제외. DEC-05: 파편 delay/life 상한이 제품 의도인지, 호출자의 요청 시간을 보장할지.

## 5. API-01 / A — 매개변수 clamp·무시 계약 조사

중복 검출과 별도 범주다. 조사 대상은 입력 보정·최대값 제한·무시 인자·용량 부족/우선순위로 생략되는 결과다. **허용 범위/단위/입력 보정/거절·축소 결과/부수효과**를 호출자와 테스트 양쪽에 명시한다. 모든 clamp를 제거하자는 뜻은 아니다.

API-01 완료 조건: 위 확인 사례에 대해 계약표·호출자 비교·경계 검증을 갖추고, 의도 불명 차이는 별도 티켓으로 분리한다. 결정은 구현+검토, 수명/연출/게임 규칙 변경은 사용자. 전체 API의 계약 감사를 끝냈다는 뜻으로 닫지 않고 확인 범위를 기록한다.

## 6. 기준 갱신과 작업 순서

1. 수정 전에 `revision_start_hashes.json` 같은 기준 해시를 보존한다. 이미 작성된 최초 조사 기준 파일을 덮어쓰지 않는다.
2. 저장소 루트에서 번들 Python으로 `Docs/QA/CodeStructure_Audit_2026-10-12/audit_structure.py`를 실행하고 `generate_appendix.py`로 파일 조사표를 갱신한다. 게임 소스는 수정하지 않으며 baseline_hashes.json은 새 기준으로 갱신된다.
3. `summary.json` 수치를 본문에 반영하고, **자동 후보 ID/위치가 바뀌면 수동 판정표도 대조**한다. 후보 수가 같아도 내용이 같다고 가정하지 않는다.
4. functions.tsv에서 파일+함수명으로 위치를 찾는다. main 내부 람다/분기는 `creditKill`, `lOnKill`, `ResetForNewGame`, `AbandonCurrentRun`, `S_CHAOS`, `DYING`를 파일 안에서 검색한다. 줄 번호는 보조 위치다.
5. 주요 전역 쓰기 위치/참조 alias와 API 계약의 변경을 재검토한다. 기준 해시가 달라지면 affected 항목을 다시 조사한다.
6. FIX-01~03 → BEH-01/02 → REG 기준 확정 → D01~06/D26 및 독립 B/C 이관 순서로 진행한다. 신규 콘텐츠는 통합 완료 영역의 공통 경로를 사용한다.

단위별 기록: 변경 ID, 기준 SHA+로컬 해시, 테스트/캡처/검색 명령, 결과, 미결정/잔여 위험, 검토자를 남긴다. 체크리스트 문서 작성은 테스트 통과나 구현 완료로 표시하지 않는다.
